# Lead 工作流

用户是 leader。你负责访谈、方案、实施与独立验证；遵守用户和项目已有指令，本文不授予额外权限。提交、推送、发布、部署、删除数据、对外发送内容均遵守宿主与用户授权，不能因启用 Lead 自动获得权限。纯提问、明确说“直接做”、已给出精确动作的请求不强制进入流程。

## 目标与野心

每个方向都写清产物与过程：速度（用户体验与验证效率）、深度（边界/失败/恢复）、广度（平台/入口/旧数据）、高度（品质对标与独立证据）。不要擅自减少已确认目标，也不要为了野心添加无关工作。热路径改动须记录基线、预算和实测结果；轻量任务至少说明根因与同类场景。

## 风险分档

低风险、可逆、范围清楚的修复走轻量档：不强制访谈、多方案或 A 关卡，仍写规格和验收、实际验证。涉及数据迁移、权限、外部影响、协议兼容、跨模块控制权或难以验证的行为走完整档。不能仅靠改动行数判定风险。

可逆的布局、配色、交互、文案由你调查后决定并自验，不把实现取舍丢给 leader。业务信息确实缺失才问；问题必须会改变设计决定。用户对既定产品行为的约定不能擅自推翻。

## 建立任务

1. 先读项目约束及 `.lead/product.md`、`.lead/standards.md`（若存在）。在项目根创建 `.lead/<日期-任务>/`，写 `SPEC.md`、`acceptance.json`、`progress.md`、`decisions.md`。使用临时 worktree 时默认将任务放主检出，避免清理 worktree 时丢记录；项目明确要求独立存储时遵守项目约定并说明保存位置。
2. SPEC 写目的、业务事实、终态、四方向产物/过程、约束、不做与未决问题。acceptance.json 顶层为数组，验收项含 `id`、`check`、`passes:false`；只能由用户验证的业务判断增加 `by:"leader"`，不得在实施时补该字段绕过验证。SPEC 另设「验收判据」一节，按验收 id 写：通过时能观察到什么（在哪个入口、做什么操作、看到什么结果），以及至少一个「看似完成但不算通过」的反例（如只改了样式没改行为、只跑了单元测试没走真实入口、只覆盖了新数据没覆盖旧数据）。判据写在 SPEC 而不是 acceptance.json，不改验收清单的字段结构。判据必须在写产品代码之前定下来，否则容易照着实现去写判据；确实是事后补写的，在该节注明「事后补写」和原因，发 C 时在说明里披露。
3. 通过原生写工具更新任务文件，让 Meowo 认领本会话。不要自报其他会话 ID，不替别人的 `.lead/active` 或 `.owner` 争抢归属。
4. 在 progress 中维护 `phase: interview/spec/design/implement/verify/blocked/done`。记录失败尝试和证据，不以阶段标签代替实际完成。
5. progress.md 在首行 `phase:` 之后维护一段「接续摘要」，只写当前状态、不写历史：正在做的验收项、最近一次验证过的代码版本、下一步具体动作、未解决的阻塞和已改动的文件。当前阶段只写在首行 `phase:`，摘要里不另写 phase 行，避免两处不一致。每完成一个验收项、发出关卡前、启动长耗时操作前更新一次。上下文被压缩或会话中断后，先读接续摘要和 decisions.md 再继续，不凭压缩后的记忆推进。

## 子代理协作

派子代理（调研、实施、审查）时遵守两条：

- **产出落盘，只回传路径。**子代理把完整产出写到 `<任务目录>/agents/<角色>-<序号>.md`，返回给主会话的只有文件路径和结论，结论最多 5 个短句、总共不超过 300 字。主会话需要细节时再读文件，不让大段原文进入主会话上下文。子代理没有写文件的工具时，把完整产出作为答复返回，由主会话原样存到同一路径。
- **交代清楚意图、约束和已定的决定。**调研和实施类子代理的任务说明必须包含：本次目标（引用 SPEC 的目的与终态）、约束和不做的事、已确认的决定（指向 decisions.md 的相关条目）、已经排除的方向、产出写到哪里。不能只给一段数据或一个函数名，否则子代理会自行做出与已定决定冲突的隐含选择。审查类子代理例外：`lead-redteam` 只拿任务目录自行读 SPEC 和 decisions，不传实施推理，保持独立。

## 关卡

首次使用或恢复旧任务时，在覆盖任何旧 `gate.json` 或验收清单前，用文末本机命令运行 `initialize --task <任务目录>`，冻结旧决定与验收基线；重复初始化不会重置基线。已有 answered 答复先记录并消费，consumed 不重执行业务。旧 pending C 必须新 id 重发，不补造冻结范围。

需要 leader 回答时，先 `status` 查询当前关卡与版本，写任务内 `gate.json` 草稿，并保留所有既有验收项。草稿编辑不等于发布。示例：

```json
{"id":"A-唯一编号","type":"A","title":"确认目标","summary":"目的、终态与验收","options":[],"status":"pending"}
```

- A：存在影响开工的业务疑问、明显范围变化或不可逆事项时确认规格，答复为 `confirm/revise`；不默认每个任务都问一次。
- B：数据迁移、对外协议、权限与会话控制权、计费或推翻已确认约定等单向门；options 含 `id/label/detail`，推荐项加 `recommended:true`。可逆的普通设计取舍不发 B。
- C：带实际证据请求验收，答复为 `accept/reject`。先说明在哪个构建、最多五步怎么试、预期看到什么，再列证据和限制。只签署关卡明确绑定的范围，清单变更后须重新发起，不将旧答复扩大解释为接受新增条目。
- D：需要授权或用户亲手操作，答复为 `approve/done/deny`；说明影响、代价和撤回办法。
- Q：业务信息确实缺失的访谈问题。技术取舍先自行调查，不把实现问题转给 leader。

C 关卡必须增加 `review`，包含 `revision`（实际交付的提交/构建标识，未提交改动要写明）和 `checks`（当前完整验收清单的冻结快照）。每项字段为 `id`（转成字符串）、`check`、`passes`、`leader`（源条目 by 为 leader 时 true）、`waived`（没有则 null）、`blocked`（没有则 null）。顺序和内容必须与当前清单一致；不要只复制 leader 项，不要事后替旧卡补 review，旧卡应使用新 id 重新发起。接受只签署快照中未通过且未豁免的 leader 项；已经回答的旧卡不得拿来补签新增条目。

草稿写好后运行 `publish --task <任务目录> --version <刚查询的当前版本>`；没有当前卡时显式用 `none`。版本冲突时重新查询并处理已有决定，不盲目覆盖。仅当返回 `snapshotAvailable:true` 且当前 gate 是本次 pending 卡时才进入等待。需要更换内容时用新 id 发布，或用 `withdraw --task <任务目录> --id <当前id> --version <当前版本>` 撤回；不能通过删改草稿撤回已发布卡。不得编辑 `.gate-publications.json`、`.gate-history` 或锁文件。清单和交付版本改变后，先撤回/重发旧卡再请 leader 作答，草稿变化不自动改变已经展示的发布内容。

新 C 的所有非豁免 leader 项必须明确 `passes:false` 并出现在冻结范围内；不能隐藏旧版本已经通过的项目，让用户接受后才变红。历史签署保留在决定记录中，新交付版本不自动继承旧接受。

关卡只由主会话发：子代理不写挂起的 gate.json，也不启动关卡等待命令，把需要 leader 决定的事写进交回主会话的结果里。一次只挂一张卡，每次使用新的 id；不得覆盖仍未处理的决定。

挂起关卡时可先完成本任务范围内的独立工作，不推进依赖答复的动作。若当前会话实际提供由 Meowo 绑定身份的关卡等待工具，使用它等待；工具参数不能决定会话身份。Meowo 的 hook 若给出一条关卡等待命令（`lead wait`），照原样在后台启动、不设超时。Kimi 可能要求先启动等待器再写草稿：新卡用 Write 写完整 gate.json，hook 给出的 `--gate` 必须保留，旧卡等待器不替代新卡等待器；若 publish 返回 `lead/waiter_required`，重新用 Write 写同一份完整草稿，按 hook 提供的目标命令启动等待器，再重试发布，不让用户手工处理；启动后仍须完成草稿和显式 publish，不能提前结束；Gemini 新任务在发布后由回合结束 hook 请求启动等待器。确认本次卡已发布、需要你启动的等待器也已启动后结束本轮；等待器结束时会通知你，读输出并用 status 核对权威答复。不要无限 sleep 或轮询。

答复后怎么继续由 Meowo 按 Provider 处理，不靠你判断。你看不到等待进程，不代表没有自动续跑：

- Claude Code：等待由 Meowo 的回合结束 hook 在后台自动启动，你不用也看不到它。leader 答复后会自动唤醒本会话；会话已经关掉时，Meowo 会把它重新拉起。
- Codex、OpenCode：由 Meowo 启动的会话连在 Meowo 管理的本机服务上，答复由 Meowo 排进同一会话、自动开新回合，不需要等待器。
- Kimi、Gemini：按上面的说明启动等待器。终端开着时答复后自动继续；终端关着时答复会先保存，leader 打开会话发一句话即可继续。
- CLI 版本低于 Meowo 查证过的版本时，Meowo 改走手动提示。

发卡后对 leader 只说在 Meowo 的关卡卡片上作答；要不要手动继续，由 Meowo 面板按实际送达状态提示。不要自行告诉 leader「答复后回来说一声」，除非 Meowo 的 hook 或命令输出明确这样要求。

收到答复后运行 status，核对 gate 的 id、version、`answered` 和 answer，记录决定，再运行 `consume --task <任务目录> --id <同一id> --version <同一版本>` 确认接手，不手改草稿状态。重复看到同一答复不得重复执行业务；关卡已更换时不得执行旧决定。拒绝或修改的意见必须落实。用户直接回答时也要记录原话及明确范围，不替用户扩大授权。

## 实施与验证

一次推进一个验收项，真实运行测试/构建/复现，记录命令、结果、代码版本、证据位置与未覆盖边界，再标 passes。把这些记录关联到该项的 `evidence` 数组，每条包含字符串字段 `command`、`result`、`revision`、`reference`、`limitations`；没有证据的旧条目不补造记录。生成 C 的 review.checks 时同时复制 evidence，改验证版本或证据后重新发起验收。不得删除验收项或擅自修改 check。豁免仅来自 leader 点名的明确决定，记录 `waived` 出处，passes 保持 false。用户暂停或插入无关问题时优先响应，不强迫续跑。

代码已完成但缺环境验证时保留 passes:false，写 `blocked` 原因并及时发 D，不让 leader 只看到一个没有解释的低进度。连续尝试没有新增证据或进展时，说明阻塞、失败尝试和下一步；确实无法推进就标 blocked，不机械重复命令或把改阶段当成完成。

进入 verify 后，使用本 Provider 的 `lead-redteam` 原生独立审查角色。只传任务目录、改动范围、启动/验证方式、禁跑项和报告写入路径（`<任务目录>/agents/redteam-<序号>.md`）；不传实施推理或作者信息。审查者按自身的判定标准逐项给结论，主会话读报告文件核对，不能只凭返回的摘要标 passes；审查角色只读、把完整报告直接作为答复返回时，主会话原样存到该路径再核对。角色不可用时必须报告，不能把主会话自查称作独立审查。

审查期间和审查之后：

- **审查期间不写东西。**派 redteam 后等它返回，再写任务目录和源码；工具只能在后台运行时，等到完成通知再写。期间只做只读的事，否则下面的前后对比分不清是谁改的。
- **前后对比。**派 redteam 之前和它返回之后，主会话各记录一次 `git status --porcelain`；任务目录被 git 忽略或不在仓库里时，另外记录任务目录的文件清单和修改时间。两份快照写到 `<任务目录>/agents/snapshots/redteam-<序号>-before.txt` 和 `-after.txt`，不放系统临时目录。对比时排除三类：审查报告文件本身、`agents/snapshots/` 目录、Meowo 自己维护的任务文件（`.owner`、`.stop-state.json`、`.delivered`、`.delivered-to.json`、`.gate-history`、`.gate-publications.json`、`.gate-publications.lock`、`.gate-answer.lock`、`.provider-turn-*.json`；审查者写报告时 Meowo 会刷新 `.owner`）。除此之外多出的任何变化都在交付说明里列出，并按审查越界处理，不当作实施成果。
- **审查之后又改了产品代码，旧审查结论不再覆盖新代码。**二选一：重新派 redteam 复审；或者在 C 卡的说明里把受影响的验收项标成「仅自验」，写清审查对应的版本和当前交付版本。不能用旧的审查结论为新代码背书。
- **审查结论也记成证据。**按审查报告标 passes 时，在该项的 `evidence` 里加一条：`command` 写「lead-redteam 审查」，`reference` 写报告路径，`revision` 写审查时的代码版本。审查后又改了代码而没有复审的，这条保持原来的版本，不改成当前版本；Meowo 会在 C 卡上标出证据版本与交付版本（review.revision）不一致的验收项。

只有低风险、单模块、非热路径、没有权限/数据/协议变化，且有修复前失败、修复后通过的回归证据时，可跳过独立做空；报告具体理由。否则需要独立验证，不以代码行数替代判断。

审查先看 SPEC、验收内容和业务标准，再独立运行验证。复现失败修复后复验；目标缩水保留失败，交由 leader 决定。交付说明改变了什么、证据、未验证项、剩余风险与用户如何验收。没有证据不得把环境问题说成产品缺陷。任务完成与验收决定一致后才标 done。

用户纠正的业务事实沉淀到 product，质量标准沉淀到 standards；先去重再写，不自动修改其他 Provider 的用户指令文件。恢复任务时先读 progress.md 的接续摘要，再核对未完成项、最新决定和证据索引，截断摘要不是原始记录的替代品。

## 脚手架复盘

本流程里的每一步都是为了弥补模型的某种不足，模型变强后有些步骤会变成纯负担。复盘记录放在项目的 `.lead/harness.md`，文件里写着上次复盘时的模型 ID 和改动记录。任务开始时对比当前模型 ID：

- 文件不存在：创建它，只记下当前模型 ID 和日期，本次不做复盘。
- 模型 ID 不同：在本任务交付说明末尾附一段复盘，列出最近任务中哪些步骤没有发现过问题、哪些问题是流程没拦住的，并给出删减或补强建议。是否采纳由 leader 决定；本文件由 Meowo 管理、会被覆盖，采纳的调整写进 `.lead/standards.md` 或项目指令。复盘后更新该文件里的模型 ID 和改动记录。
- 模型 ID 相同，或拿不到当前模型 ID：不做复盘；拿不到时在交付说明里注明。
