# 记下纠正（分层）

团队怎么运作见 `{{TEAM_DIR}}/knowledge/shared/README.md`。

**只写个人层和项目层，从不写 `{{TEAM_DIR}}` 下的文件，也不改各 Claude 配置目录里 `agents/`、`skills/` 下的团队文件。** 那些是 Meowo 托管的，升级会覆盖，写进去的纠正会丢。

## 步骤

1. **确认是谁的活、哪条纠正。** 用用户原话，不改写成更强或更弱的意思。
2. **判断层次：**
   - **专业功底**：换任何项目都成立的专业判断（「层级不清」「迁移脚本要能回滚」「测试要做变异检查」）。→ 个人层 `{{PERSONAL_DIR}}/knowledge/<角色>/lessons.md`（角色：`pm`、`designer`、`developer`、`reviewer`）。
   - **项目约定**：只对这个项目成立（「这个项目要活泼」「这里用 pnpm」「这个 App 首页按事件组织」）。→ 项目 Lead 目录的 `standards.md`（质量标准）、`product.md`（业务事实）或设计规范文件（`design-style.md`）。
   - **用户品味**：用户个人的偏好，跨项目都适用，但不是行业通用的专业判断（「不要渐变紫」「先说结论」）。→ 品味清单：读 `{{PERSONAL_DIR}}/config.json` 的 `taste` 字段拿到路径，按清单原有的格式追加，括号注日期和场景；角色的 lessons.md 里只留一行指向。
     - 没配 `taste`、或 `config.json` 不存在：新建 `{{PERSONAL_DIR}}/taste.md`（开头写两行说明：这是你的品味清单；想放到自己的 git 仓库或网盘，就把文件挪过去，再把路径写进 `config.json` 的 `taste`），把这一条写进去，并告诉用户文件在哪。
     - 配了 `taste` 但文件读不到（例如网盘没挂载）：不另建文件，告诉用户「品味清单读不到，这条先没记」，并把要记的原文给他。
   - 拿不准就问用户一句：「这条是只对这个项目，还是以后所有项目都这样？」附推荐答案。
3. **先查重。** 读目标文件，已经有同类条目的：在那条后面补这次的日期和场景，并在角色 lessons.md 的记录行尾加「重复」，统计里的重复次数加 1。重复说明上一次没记好或没用上，顺手看看是哪个环节漏了（没读？读了没照做？写得太含糊？），把改法也写上。
4. **写成能执行的规则**：「以后怎么做」要具体到下一次交付前能自查的程度，不写「注意细节」这种空话。
5. **碰到底线时照记，但不覆盖底线。** 用户要放宽的是托管层标了「底线」的条目（可访问性、数据安全、不可逆操作要确认、可回滚、硬底线五样）时，可以记下来，但在条目里注明「底线不可覆盖：角色遇到时仍会报出来，请你定」。
6. **更新统计**：角色 lessons.md 的被纠正次数加 1。文件不存在就新建，开头写格式说明和统计两行。
7. **告诉用户记在了哪一层、哪个文件、加的是哪一条。** 用户可能正开着这个文件编辑，保存时会把刚加的这条覆盖掉；写清楚加了什么，他可以补回来。

## 定期整理

某个角色 lessons.md 里功底类条目攒到 10 条以上，或同类条目出现 3 次以上，提议把它们并进个人层的 `{{PERSONAL_DIR}}/knowledge/<角色>/craft.md`（并入时保留出处），并告诉用户。角色开工时会连同托管功底一起读它。

## 不做

- 不把一次性的决定（「今天先别合」）当规则记。
- 不替用户扩大纠正的范围：只对这个项目说的，不写成全局规则。
- 不写 `{{TEAM_DIR}}`、`agents/`、`skills/` 下的托管文件。
