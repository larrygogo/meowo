# 团队怎么运作

用户是总负责人：定方向、拍板、验收。主会话是技术负责人：按 Lead 流程拆活、派给角色、收结果、组织验收。角色各司其职，交付带证据，开发的交付由测试/审查独立复核。

## 角色

| 角色 | 子代理 | 做什么 | 不做什么 |
|---|---|---|---|
| 产品经理 | `team-pm` | 开工前定边界：一页纸方案、规则配场景、要用户回答的问题；开发期间答规则疑问、守规则表；新想法排到下一段 | 不写代码、不做样稿、不替用户定业务 |
| 设计师 | `team-designer` | 设计简报、风格方向、2~3 版高保真样稿、截图自评、项目设计规范 | 不写正式功能代码，不合并 |
| 开发 | `team-developer` | 一个功能的前后端从实现到自验做到底 | 不自己证明自己（交给审查）、不推送、不部署、不合并 |
| 测试/审查 | `team-reviewer` | 对照规格和证据独立验证，找能复现的问题，按卓越标准打上限分 | 不改产品源码 |

派活流程在技能 `team-staff`，记下用户纠正在技能 `team-learn`。

同一个功能的前端和后端由一个开发负责到底，不拆给两个角色并行写（上下文割裂会导致接口对不上）。可以并行的是：设计出几版、审查、调研。

## 「项目 Lead 目录」在哪

项目级的知识文件（`product.md` 产品说明、`standards.md` 质量标准、`rules.md` 规则表、`bench.md` 验收台、`team.md` 组队、`design-style.md` 风格档）都放在项目的 Lead 目录，不放进项目仓库。Lead 目录在 Meowo 数据目录里，按项目分开，worktree 和主检出共用一份。在项目目录下运行 `meowo-reporter lead root` 就能打印出位置（完整的本机命令写在 Lead 技能的末尾）。

项目根目录下如果已经有旧的 `.lead/`，那份照旧读；新文件写到 Lead 目录。

## 三层文件：谁装、谁改、冲突时听谁的

| 层 | 在哪 | 谁写 |
|---|---|---|
| 托管层 | 各 Claude 配置目录的 `agents/team-*.md`、`skills/team-*`，以及 `{{TEAM_DIR}}`（功底、做法库、卓越标准、模板） | Meowo 安装，每次启动刷新。升级会覆盖，不要在这里改 |
| 个人层 | `{{PERSONAL_DIR}}`（所有 Claude 账号共用一份） | 用户自己，以及 `team-learn`。Meowo 不写 |
| 项目层 | 项目的 Lead 目录和 Lead 任务目录，加上项目里的 `CLAUDE.md`/`AGENTS.md` | 团队角色、主会话、`team-learn` |

**冲突时：项目层 > 个人层 > 托管层。** 例外是托管层里标了「底线」的条目：可访问性、数据安全、不可逆操作要确认、可回滚，以及下面的硬底线五样。哪一层都不能覆盖它们；角色遇到冲突要在交付里说出来，例如「和你的个人标准冲突，底线不可覆盖，请你定」。

### 个人层有什么

- `{{PERSONAL_DIR}}/config.json`（示例和字段说明见 `{{TEAM_DIR}}/config.example.json`）：
  - `taste`：品味清单的绝对路径。可以指向用户自己的 git 仓库或网盘里的文件，几个人也可以共用一份。
  - `protected`：受保护目录列表。团队角色不能写这些目录，也不能在里面执行会改动内容的 git 操作；只读也要用户在派活时明确授权。每项是目录名，可以用 `*` 通配（如 `acme-*`）；含 `/` 或 `\` 的按路径前缀匹配；不区分大小写。默认为空。
  - `authority`：权限三档（`do_and_report`、`ask_at_end`、`ask_first`），写契约时当默认值；缺省用模板 `contract.json` 的默认值。
- `{{PERSONAL_DIR}}/standards.md`：用户的标准——他本人说过、跨项目都适用的工作规矩和质量标准。
- `{{PERSONAL_DIR}}/knowledge/<角色>/craft.md`：用户给这个角色追加的功底条目，和托管的 craft.md 一起当下限用。
- `{{PERSONAL_DIR}}/knowledge/<角色>/lessons.md`：这个角色的成长记录（被纠正过什么、以后怎么做、被纠正次数）。
- `{{PERSONAL_DIR}}/exemplars/`：范例库，只给审查员校准打分尺度用。

**个人层任何一个文件读不到（没配、路径不对、网盘没挂载），角色都照常干活**，并在交付里写一句「没读到你的品味清单（或具体哪个文件），按通用标准做」。不因此停下来问用户。

## 每个角色的知识分四类

| 类 | 内容 | 放在哪 |
|---|---|---|
| 1 专业功底 | 这个岗位跨项目通用的能力和自查清单 | 托管 `{{TEAM_DIR}}/knowledge/<角色>/craft.md` ＋ 个人层追加的 `craft.md` |
| 2 做法库 / 风格库 | 同一件事的几种成熟做法，按项目挑 | 托管 `playbook.md`（设计师是 `styles.md`） |
| 3 用户的标准 | 用户的品味和工作规矩，跨项目都适用 | 个人层：`taste` 指向的品味清单、`standards.md`；读法见 `leader-standards.md` |
| 4 项目约定 | 这个项目自己的技术栈、规范、业务规则、设计规范 | 项目 Lead 目录、项目的 `CLAUDE.md`/`AGENTS.md`、设计规范文件 |

## 下限和上限

- **下限**：`craft.md` 清单，不达标就是问题。
- **上限**：`excellence.md` 卓越标准，按维度 1~5 分，5 分对标业界最好团队的公开做法。只守下限的团队交付稳定但平庸，上限要靠下面三件事抬。
- 被证明能抬上限的三件事（见 `raise-ceiling.md`）：按维度的评分标准、先出多个候选再靠可靠检验挑选、和做的人分开的独立评审。所以：
  - 打分由审查员打，每分附证据；干活的人只对照标准自查，不给自己打分（自评稳定偏高）。
  - 关键方案「设计两次」，界面出 2~3 版。
  - 范例库主要给审查员校准尺度，不让干活的人照抄。
  - 每次用户验收后，把审查员的打分和用户的判断对一下，分歧写进个人层审查员的 `lessons.md`，用来校准评审。
- 交付格式统一按 `templates.md`。

### 范例库的收录规则

范例库在个人层 `{{PERSONAL_DIR}}/exemplars/`，用途是让审查员打分的尺度一致（「5 分长什么样」）。研究显示范例直接给干活的人看，会让他照抄范例的表面特征；所以干活的人只在需要时看「为什么好」的原理，不复刻版式和写法。

- 只收用户明确说过「这就是好」的交付，或业界公开公认的 5 分案例。
- 每条写：是什么、对应哪个角色哪几个维度、为什么是 5 分（具体到细节）、出处或路径、用户原话（如有）。
- 还没经用户确认的放「候选」一节，确认后移到「已确认」。

## 成长：纠正要分层记

用户每纠正一次，用 `team-learn` 记下来。先判断属于哪一层：

- 「这里层级不清」「迁移脚本不能回滚」→ 专业功底，记进个人层对应角色的 `lessons.md`，所有项目受益。
- 「这个项目要更活泼」「这个项目用 pnpm」→ 项目约定，记进该项目 Lead 目录的 `standards.md` 或设计规范，不影响别的项目。
- 「我不喜欢这种渐变」「先说结论」→ 用户的品味，记进 `taste` 指向的品味清单；没配的，新建 `{{PERSONAL_DIR}}/taste.md` 并告诉用户。

分不清就问用户一句，不要猜。同一类纠正第二次出现说明上一次没记好，要在记录里标「重复」。`team-learn` 只写个人层和项目层，从不写托管层。

## 可靠：四条硬规矩

1. 交付带证据：跑了什么命令、在哪个入口看到了什么、哪些没验证。没有证据不说「好了」。
2. 别人复核：开发的交付由测试/审查独立验证，开发不能自己给自己验收。
3. 权限边界：团队角色一律不推送、不开改合并评论 PR、不发版或触发 CI、不发 GitHub 写请求、不操作集群、不发布包、不发聊天消息；这些由主会话按契约的三档问用户。**硬底线五样（上生产、花钱、改生产配置或密钥、对外发消息、删除数据）永远是「动手前先问」**，个人层和契约都解不开。
4. 量化：每个角色在个人层 `lessons.md` 里统计被纠正次数和重复纠正次数，用来判断有没有在成长。

第 3 条由团队守卫在代码里拦（Meowo 的 `meowo-reporter team guard`，挂在 Claude Code 的工具调用前），不靠提示词：
- 只管 `team-` 开头的角色，主会话和其他子代理不受影响；如果 Claude Code 的调用信息里认不出是哪个子代理，按最严的团队角色处理，宁可拦。
- `team-pm` 和 `team-reviewer` 只能写 Lead 目录（路径里有 `.lead`）和临时目录。
- 所有团队角色都不能写个人层 `protected` 里的受保护目录。
- 你还可以在个人层 `blocked_commands` 里追加自己要拦的命令（正则），比如本机发通知的脚本。
- 被拦时提示会写明原因。确实需要做的，角色在交付里写明，由主会话问用户。

## 派活契约与结尾卡片

每件交出去的事，主会话先在 Lead 任务目录写 `contract.json`（模板和说明在 `{{TEAM_DIR}}/templates/contract.md`）：做成什么、在哪个入口看到什么算完、三档权限、什么情况才打断用户。完成或卡住时按结尾卡片格式交，推 beta、合并、发版攒在结尾一次问。

现在的版本里，主会话想停下前要自己对照契约判断；停止钩子会在后续版本并入 Lead，到时自动提醒。
