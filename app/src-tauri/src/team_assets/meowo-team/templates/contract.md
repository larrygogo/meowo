# 派活契约怎么写

契约就是交出一件事时讲清楚的四件事：做成什么、做到什么程度算完、这次能直接做什么、什么情况才来打断。对应契约式设计的三件套——前置条件（规则和输入讲清了，产品经理负责）、后置条件（完成标准）、不变式（权限边界）。

## 什么时候写

主会话（技术负责人）接到一件要做的事、确认完要什么之后，立刻在 Lead 任务目录写 `contract.json`，和 SPEC.md 放一起（复制 `{{TEAM_DIR}}/templates/contract.json` 改，**把 `status` 从模板的 `draft` 改成 `active`**）。用 Write 或 Edit 工具写。

给用户看一眼：一句目标 + 完成标准列表 + 跟默认不同的授权。用户回「好」或改一句，就开干。

现在的版本没有停止钩子替你守契约：主会话想停下之前，自己对照契约判断一次。停止钩子会在后续版本并入 Lead，到时按下面的 `status` 规则自动提醒；现在就照这套规则写，升级后不用改。

## 字段

- `goal`：一句话。
- `done`：完成标准。每条写清 **在哪个入口**（用户会用的那个：安装版、测试环境、后台页面、真机）、**做什么**、**看到什么**、**证据**。「单元测试通过」「代码已提交」不能当完成标准。项目有 Lead 目录的 `bench.md` 验收台的，入口和操作照它写。验证过一条就把 `passes` 改成 true。
- `authority`：三档权限。默认值按这个顺序取：
  1. 个人层 `{{PERSONAL_DIR}}/config.json` 的 `authority`（用户自己调过的三档）；
  2. 读不到或缺某一档，用模板 `contract.json` 里的默认值，并告诉用户「没读到你的权限设置，用的默认三档」。

  三档的意思：
  - `do_and_report` 直接做，结尾卡片里汇报；
  - `ask_at_end` 攒到结尾一次问（推 beta 也在这里：连着很多小改动，不能每次都推）；
  - `ask_first` 动手前必须先问。

  **底线：上生产、花钱、改生产配置或密钥、对外发消息、删除数据这五样永远在 `ask_first`。** 个人层的设置或用户的原话把它们挪到别的档，都不挪；在契约里注明「这是底线，不能放开」并告诉用户。

  这次任务有特别授权（比如用户说「这次直接推 beta」），就把那一项挪档，并在旁边写上用户原话和日期。任务进行中用户改了个人层设置：收紧的马上照新的做，放宽的只对新开的任务生效。
- `interrupt_when`：只有这些情况才停下来找用户。
- `status`：
  - `active` 正在做。想停之前先对照契约判断一次：接着做，还是按规矩停下（做完了、需要用户决定、在等后台任务、用户让停）。
  - `waiting` 在等后台任务（CI、部署、编译、子代理）。`waiting_for` 写在等什么、它结束时怎么通知你。**被通知唤醒后先改回 `active` 再干活。**
  - `needs-user` 碰到打断条件。`for_user` 写清要用户决定的事，每条附推荐。**用户回答后先改回 `active`**（还有没答的，就重写 `for_user` 只留没答的）。
  - `paused` 用户明确说了停（「先停」「先别做了」）。**把用户原话一字不差写进 `paused_quote`。**「做完 X 告诉我」「汇报一下进度」不是让你停：把整件事做完再交结尾卡片，想同步进度就在继续干活时顺带说一句。用户之后又说话：让你继续就改回 `active`；仍要你停或在聊别的，就保持 `paused`。
  - `draft` 模板默认值，还没启用。
  - `done` 完成标准全部 `passes: true`。
- `for_user`：结尾要问的事、需要用户亲手做的一步，都写在这里，结尾卡片照抄。

## 结尾卡片

完成或要用户决定时，回复用户只用这个格式：

```
# <一句话：做成了什么 / 卡在哪>

## 在哪里看
<入口、操作、预期看到什么；截图路径>

## 我替你定了的事
<可撤回的取舍，每条一句。不同意的划掉，会记进品味清单或项目规则表>

## 需要你决定 / 需要你做
<ask_at_end 攒下来的事（推 beta、合并、发版）和打断条件，每条附推荐>

## 没验证的 / 剩余风险
<包括角色交付里说「没读到品味清单」之类的个人层缺失>
```

卡在只有用户能做的一步时，标题直接写「还差一步：需要你……」，不写「已完成」。
