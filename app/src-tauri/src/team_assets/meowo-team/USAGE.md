# 团队使用说明

这套做法的目标：你交出一件事以后，只在**开头**（把边界说清楚）和**结尾**（验收）出现。中间不用按「继续」，不用当测试，不用替 agent 做小决定。

它要解决的是和 agent 协作时最常见的几种空耗：agent 汇报完就停下等你说「继续」；等后台任务时没醒；把能撤回的小决定抛给你；还有「做完了」不可信——它的「完成」停在了代码层面，没生效到你在用的那个程序里。

团队有四个角色：产品经理 `team-pm`、设计师 `team-designer`、开发 `team-developer`、测试/审查 `team-reviewer`。主会话当技术负责人，按 Lead 流程派活。团队只在 Claude Code 里可用。

## 你只做两件事

1. **开头**：说清要什么。大功能会有产品经理来问你一轮问题，**一次答完**。
2. **结尾**：看结尾卡片，在卡片写的入口里看一眼效果；推 beta、合并、发版这些事在这里一次批完。

中途有新想法，直接说就行。它会被记进「下一段」，等这一段做完再处理，不会插进正在做的这一段。

## 三种用法

### 一、大功能或新项目

> 你说：「让团队来做：<需求，一段话就行>」

1. **产品经理先定边界。** 它交回三样东西：
   - 一页纸方案：做成什么样、投入上限、不做什么、撤不回的决定、要先探明的风险、分几段做；
   - 一张规则表：每条规则配 3 个以上的具体场景，专门挑换设备、重置、断网恢复、多人共用这类边角情况；
   - 一组问题：只问会改变做法的业务问题，每个都附推荐答案。

   你一次答完。
2. **主会话写一份派活契约，给你看一眼。** 内容是目标和完成标准，完成标准写的是「在哪个入口、做什么、看到什么」。你回「好」，或者改一句。
3. **中间不用管。** 设计、开发、审查各自做。开发碰到规则没写到的情况，先问产品经理；在边界之内的它直接定，事后告诉你；碰到边界的，才攒起来问你。
4. **结尾卡片：**
   - **在哪里看**：入口、操作步骤、预期看到什么、截图；
   - **我替你定了的事**：可撤回的取舍，你不同意的划掉，它会记进你的品味清单或项目规则表；
   - **需要你决定**：推 beta、合并、发版，加上打断条件里攒下的事；
   - **没验证的 / 剩余风险**。

### 二、修 bug、小功能

> 你说：「按契约做：<事情>」

跳过产品经理这一步。主会话直接写契约，你看一眼完成标准，然后等结尾卡片。

### 三、界面

和第一种用法一样。区别是：设计师动笔前，会先用三句话说明这一屏的思路（给谁用、用户最想完成什么、什么最重要），再并排给出 2~3 版。思路不对，你在三句话那一步就能拦下来。

设计师要读项目的产品说明（Lead 目录的 `product.md`）。没有的话，产品经理会先找你聊一次，把它起草出来。

## 权限三档

写在每份契约里的默认值：

- **直接做，事后汇报**：范围内的修改、测试、构建、本地提交；顺手修的小问题；清理已经合并的 worktree 和分支；可撤回的取舍（布局、配色、交互、文案、默认值、实现方式）。
- **攒到结尾一次问**：推 beta、合并到主分支、发版。
- **动手前必须先问**：上生产、花钱开机器、改生产配置或密钥、对外发消息、删除数据。

想长期调整，改个人层的 `config.json` 里的 `authority`（见下一节）。某次想放宽，直接说就行，比如「这次直接推 beta」，它会把那一项挪到「直接做」，并记下你的原话。

**最后一档里的五样是底线，个人层和契约都放不开。** 即使你在设置里把「对外发消息」写进「直接做」，主会话照样先问你，团队守卫也照样拦。

## 你的个人设置（个人层）

团队的通用文件由 Meowo 安装和刷新；你自己的东西放在个人层 `{{PERSONAL_DIR}}`，Meowo 不会改它，所有 Claude 账号共用一份。什么都不配，团队也能用，只是按通用标准做，并在交付里说明「没读到你的品味清单」。

- `config.json`（照着 `{{TEAM_DIR}}/config.example.json` 写）：
  - `taste`：你的品味清单放在哪。可以是你自己 git 仓库或网盘里的文件。
  - `protected`：不许团队角色碰的目录，比如公司或客户的项目。写目录名，可以用 `*` 通配（`acme-*`），也可以写路径前缀。
  - `authority`：你的权限三档。
- `standards.md`：你跨项目都适用的标准和工作规矩。
- `knowledge/<角色>/craft.md`：你想给某个角色追加的功底条目。
- `knowledge/<角色>/lessons.md`：角色的成长记录，`team-learn` 会往里记。
- `exemplars/`：你认可的「这就是好」的交付，审查员用来校准打分。

你纠正某个角色时（「记住」「以后别这样」），主会话用 `team-learn` 把这条分层记下：只对这个项目成立的记进项目 Lead 目录，跨项目的品味记进你的品味清单，角色的专业功底记进个人层的 `lessons.md`。它会告诉你记在了哪个文件。

冲突时项目的约定优先于你的个人设置，你的个人设置优先于通用文件；但通用文件里标了「底线」的（可访问性、数据安全、不可逆操作要确认、可回滚、上面五样），哪一层都改不了，角色遇到冲突会在交付里说出来，请你定。

## 你会看到的变化

- **「完成」的意思变了。** 现在的完成是指：在契约写的入口里能看到效果，有截图，截图里带版本号。如果卡在只有你能做的一步（配权限、真机、付款），卡片标题会直接写「还差一步：需要你……」。
- **团队角色碰不了对外的东西。** 推送、开或合并 PR、发版、触发 CI、操作集群、发布包、发聊天消息，团队角色一律被守卫拦下；产品经理和审查员只能写 Lead 目录和临时目录。需要做的，由主会话按三档问你。
- **派活契约。** 主会话想中途停下前，会先对照契约判断：接着做，还是按规矩停下（做完了、需要你决定、在等后台任务、你让它停）。现在这一步靠主会话自觉；停止钩子会在后续版本并入 Lead，到时同一次停顿会被自动提醒一次。

## 第一次在一个项目里用

项目里有两份文件是给团队读的，没有的话会标「待建」：

- **产品说明**（Lead 目录的 `product.md`）：给谁用、核心场景、每个功能为什么存在、什么最重要。由产品经理找你聊一次后起草。
- **验收台**（Lead 目录的 `bench.md`）：在你会用的那个入口里，怎么看到改动的效果，包括怎么构建、安装、登录、截图、确认版本。由开发第一次在这个项目做验收时建好，之后每次都照着用。

这两份文件放在 Lead 目录（Meowo 数据目录里），不写进项目仓库。模板在 `{{TEAM_DIR}}/templates/`。

## 已知限制

- **只支持 Claude Code。** 其他 CLI 里说「让团队来做」，Lead 照常工作，但不会派出团队角色。
- **契约不会自动启用。** 你要说「让团队来做」或「按契约做」它才启用。想让每次派活都默认用契约，可以在你自己的全局 `CLAUDE.md` 里加一句。
- **子代理中途停下不会被拦。** 开发、设计中途停下，靠主会话收到交付后对照契约检查。
- **已经开着的会话要重开，才会加载新装的角色和技能。**
- **产品经理推演时序冲突要多看一眼。** 规则表里涉及「之后」「下一次」「重新」的条目，最容易出现两句话单独看都对、放在一起打架的情况，值得你多看一眼。
- **记进品味清单时，你正开着这个文件。** 你保存时会把刚记的那条覆盖掉；`team-learn` 会告诉你加的是哪一条、在哪个文件，可以补回。

## 怎么关掉

- **整个关掉**：在 Meowo 设置里关掉「团队」。Meowo 只删它装的文件，你的个人层不动。
- **只停用某个角色**：这一版还没有单个角色的开关。直接删角色文件不算停用，下次启动 Meowo 会被装回来。
- **这一次先停**：直接说「先停」。

## 文件在哪

- 角色：各 Claude 配置目录的 `agents/team-pm.md`、`team-designer.md`、`team-developer.md`、`team-reviewer.md`
- 技能：`skills/team-staff`（组队与派活）、`skills/team-learn`（记下纠正）
- 通用知识：`{{TEAM_DIR}}/knowledge/<角色>/`（功底、做法库、卓越标准），团队怎么运作见 `{{TEAM_DIR}}/knowledge/shared/README.md`
- 模板：`{{TEAM_DIR}}/templates/`
  - `contract.json`、`contract.md`：契约，以及结尾卡片格式
  - `brief.md`：一页纸方案
  - `rules.md`：规则表
  - `product.md`：产品说明
  - `bench.md`：验收台
- 你的个人设置：`{{PERSONAL_DIR}}`，示例 `{{TEAM_DIR}}/config.example.json`

以上托管文件升级时会被覆盖。想长期保留的改动写进个人层。
