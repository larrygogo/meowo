# 发布说明怎么写

`vX.Y.Z.md` 会原样出现在三个地方：应用内更新窗口、GitHub Release、官网更新日志页。读者是正在决定要不要更新、或者刚更新完想知道有什么可试的用户。写给他们，不写给开发者。

发版前 `node scripts/check-release-notes.mjs docs/release-notes/vX.Y.Z.md` 会检查长度和明显的开发者内容，release.yml 在构建前也会跑它，不通过就不发。脚本只拦得住常见说法，下面的规则以人读为准。

## 结构

```markdown
一两句话：这一版最值得试的一到三件事。

## 新功能
- 每条一件用户能做的事

## 改进
- 原来能做、现在更好用的事

## 修复
- 用户遇到过的症状，写成现在的样子

## 注意
- 只在用户需要做点什么时写：试用版怎么回退、某个设置被重置、需要重新登录
```

「注意」也用来交代用户会找的东西：去掉或挪走的入口、改了含义的快捷键、会自动关掉或删掉的东西、默认行为的变化。删减条目时这类最后才删。

试用版（`vX.Y.Z-beta.N`）照同样的写法和上限，「注意」里写清怎么回到稳定版、会不会自动更新。

没有内容的小节就不写。改动多的版本可以把「新功能」换成两三个按主题命名的小节，比如「灵动岛」「手机页」，但全篇条目总数不变。

## 长度

- 开头一段不超过 120 字。
- 全篇最多 20 条，每条不超过 50 字。正文合计不超过 1500 字。
- 超了就删，不要压缩措辞硬塞。用户 30 秒读不完的部分等于没写。

## 写什么

- 先写对用户的好处，再写怎么用。「长会话打开更快」好过「优化了时间线归并」。
- 一条只说一件事。操作入口写清楚：在哪里点、按什么键。
- 修复写现在的结果，让人一眼看出问题已经没了：「窗口拉矮时也能看到审批卡里的命令」「看过的会话不再亮未读点」。不要只写症状，读起来像现在还有这个 bug。不写原因，不写「此前…现在…」的来龙去脉。
- 同类的小修小补合成一条：「对话窗、侧栏几处显示问题」。
- 只对一家 agent 或一个平台生效的，在条目里点名：「Kimi 会话里换模型不再失败」。

## 不写什么

- 测试和验证情况：用例数量、「测试底盘」、哪些没在真机上验证过。这些放 PR 描述。
- 依赖升级、漏洞编号（CVE、RUSTSEC）、CI、e2e、构建脚本。修了用户受影响的安全问题时写一句「修复了一个安全问题，建议更新」。
- 官网、README、文档的改动。
- 实现方式和参数：轮询间隔、超时秒数、文件路径格式、组件名、内部函数名。
- 只有开发者看得出的视觉细节：图标线宽、对齐、圆角、对比度数值。真要提，合成一句「界面细节打磨」。
- 本版之内引入又修掉的问题。用户从没见过它。

## 用词

- 遵守项目的文案风格：短句，不用破折号和分号，不用口号式标题，不用三连排比，少用「一键」「直接」「无缝」。
- 状态词和界面上的叫法一致，按钮名用「」括起来。
- 快捷键可以写，但只写在用户会想用的功能后面，不要整条罗列。

## 例子

改前：

> 未跟踪文件超过 50 个的目录折成一行，可以点开，也可以整个目录暂存、放弃或「加入 .gitignore」

改后：

> 未跟踪文件很多的目录折成一行，可以整体暂存、放弃或忽略

改前：

> 面板收起时 agent 操作的网页视口只有 2×2，截图超时

改后：

> 面板收起时，agent 也能截取网页
